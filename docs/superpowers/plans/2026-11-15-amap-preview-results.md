## 16:26 后续诊断：定位官方路线组件错误（2026-11-15）

重新使用独立 Chromium 上下文实测官方组件，诊断脚本：`验证工具/check-amap-official-diagnostic.cjs`。脚本仅输出服务路径、参数名称、状态及安全摘要，不输出高德密钥、完整 URL 或原始响应体。未修改正式旅行存储、主页面、共享地图代理。

**原因已用 A/B 对照确认：** 当前 `旅迹风格预览/amap-proxy.cjs` 将上游高德带 `callback` 的 JSONP 结果沿用上游 `application/json` / `application/octet-stream` 响应类型，并附带 `X-Content-Type-Options: nosniff`。高德 JS API 以脚本方式加载 JSONP 时会因此回调 `error`，即使上游路线数据的 `status=1`、`infocode=10000`、`info=OK`。原始诊断：`node 验证工具/check-amap-official-diagnostic.cjs` 返回 `error`；只在隔离浏览器拦截本机代理响应、将带 callback 的响应类型临时改成 `application/javascript; charset=utf-8`（不改变内容或正式服务）后，`node 验证工具/check-amap-official-diagnostic.cjs --jsonp-mime --all` 对四种组件全部返回 `complete`。未观察到页面未捕获异常。

### 公交参数与 cityd=NaN 的根因

19:27 与 19:52 两轮真实请求都观察到代理请求带 `cityd=NaN`（同城查询仍返回成功）。阅读高德 JS API 2.0 的 Transfer 插件源码确认：SDK 构造请求时执行 `params.cityd = +cityd`，把 cityd 强制转成数字，传入城市名（如“青岛市”）就得到 `NaN`。城市名只对 `city` 参数有效。

修复：后端新增 `/api/places/city-code`，复用既有城市行政区查询与 24 小时缓存，把城市名解析为数字城市码（高德返回 0532 这类代码）；前端在每次公交查询前解析终点城市码作为 `cityd`，解析失败时省略该参数而不是传城市名。起点城市缺失时沿用行程目的地作为同城回退，不再出现 `NaN`。

20:02 真实复验两次公交请求：`city=青岛市`、`cityd=532`（0532 去掉前导零），两次均 HTTP 200 并返回 5 个方案；策略、日期、时间参数均已带上。20:03–20:04 `check-next-map-live.cjs` 完整 PASS：四种官方组件均成功、JSONP MIME 正确、公交第 2 个方案保存 4017 秒与卡片一致。
