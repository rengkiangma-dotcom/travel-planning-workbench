# 评论驱动的真实行程与地图 — 实施计划

> **执行方式：** 使用 Superpowers `executing-plans` 和 `test-driven-development` 在当前本地预览中逐项执行；每个涉及持久化的操作先写回归检查，再实现并验证。当前目录不是 Git 仓库，不创建提交，也不触碰用户浏览器的数据。

**目标：** 让用户从真实地点搜索或已有安排出发，手动建立每天可编辑、可保存、可在真实地图上查看的行程，形成可验证的第一阶段；保留后续交通、住宿、协作和智能规划的扩展位置。

**架构：** 保留现有本地服务、高德和 12306 接口。行程中的地点用已有 `plans` 数组保存稳定 ID，真实地点详情另存 `customPlaces`；老的示例地点及本地数据继续兼容。地图根据地点来源使用对应坐标，候选地点与当日地点同时显示。浏览器操作测试使用独立无头 Edge 上下文。

**技术：** 静态 HTML/CSS/JavaScript、Node 本地接口、AMap JS 与 Web 服务、Playwright。

## 评论、用户要求与取舍

| 依据 | 应解决的问题 | 本轮实现与边界 |
|---|---|---|
| R0299、R0482、H0025：地图、每日地点与交通一起看 | 真实地点只是临时查看，不能编排 | 真实搜索地点可确认名称地址后放入指定日期；地图显示当天所有点。道路路线与示意线分开标明 |
| M0026：同名地点可能走错 | 地址和坐标不能只按名称猜 | 使用搜索结果的高德 ID、完整地址、城市及坐标，用户自行选；不自动把同名地点合并 |
| R0012、R0559、R0571；用户要求先问有无行程、保留手动选择 | AI 不应挡住直接操作 | 已有分支和填空保留；新地点支持按钮手动添加、移动、移除和撤销，不强制对话 |
| R0178、R0485：待规划与已排地点要对照 | 地点不应被迫立即确定日期 | 支持先保存真实地点到待规划池，可在地图与当日已选点同时显示，之后再加入具体日期 |
| M0018、R0281；用户要求确定去返程和住宿 | 车站、住宿、预约不应被无声覆盖 | 在每日安排显示已选交通、已填住宿及预约原文，明确尚未自动解析或校验时间；不虚构时间或已购票状态。完整冲突引擎另列后续 |
| R0491、R0426：怕内容丢失 | 改数据可能导致存档无效 | 修改读取校验兼容原记录；添加回归测试覆盖旧行程、真实地点、撤销、刷新。继续保留原行程文字 |
| R0044：直线与真实交通不同 | 不可把示意线当导航 | 保留现有两点高德路线查询；每日顺序线明确标识示意。完整多段交通和约束联动属于第二阶段 |
| 用户明确桌面优先、地图默认打开、同按钮开关 | 功能修改不能破坏工作台布局 | 桌面左右两栏、默认展开和同一开关保留；不做手机 App |

### 补充任务：当天相邻地点查询真实交通

**依据：** 用户明确要求在地图上形成路线；R0482 赞赏查看公共交通、驾车和步行时间，R0044 强调直线距离不能代替实际出行。

**修改：** `旅迹风格预览/live-data.js`、`app.js`、`amap-map.js`、`workspace.js`；**新增测试：** `验证工具/check-daily-route.cjs`。

- [x] 每天有两个及以上带有效坐标的地点时，用户可选择公交、驾车或步行，查询当天相邻地点的每一段高德路线；不隐式包括未加入行程的酒店或车站。
- [x] 每段显示起终点、查询时间、距离、时长和可用费用；没有结果或接口失败显示明确原因，不以直线冒充真实路线。

## 第二阶段及以后（不纳入本次实现验收）

- 已购票、住宿晚数、预约时间的结构化数据与冲突判断；实际路线的换乘详情和自动重试。
- 可恢复的备份、图片/长图导出、多行程及只读/多人协作。
- 与真实模型对接的可选 AI、图文链接导入；用户不需要靠粘贴开始已有行程。
- RollingGo 酒店报价需单独的有效 Key，机票价格需实际供应商；未经实测不得称为已可查询。手机 App 按用户要求后置。

## 范围自查

本计划是针对评论中最基础的真实地点与地图缺口，不把全部 741 条评论都转成首屏功能。评论是历史样本而非普遍比例；价格、路线与位置均以接口实际返回和查询时间为准。计划没有要求清除用户数据、提交、部署或向他人发送信息。
